### Description(上限 16,000 字元)

```
104 的資料庫其實記錄了每個職缺「上次處理履歷」和「上次回覆應徵者」的時間,而且 104 網頁自己載入職缺時就會把這些欄位抓回你的瀏覽器。但 104 只會在頁面上顯示正面的那一半(例如「7 天內處理過履歷」),從不告訴你這家公司近 30 天內一個應徵者都沒回覆過。

這個外掛把另一半補上。

▍它會顯示什麼

在 104 的搜尋結果、AI 推薦、職缺內頁和公司頁,每個職缺會多出一列數據。收合狀態就全部呈現,不必展開:

處理履歷 ✓ 3 天前   回覆應徵者 近 30 天內無紀錄   應徵 6 人
刊登 2026/07/02(65 天前)   重新刊登 2 次   公司開缺 12 個

・處理履歷 — HR 最後一次處理履歷是幾天前;這是 30 天的滾動紀錄,超出就顯示「無紀錄」
・回覆應徵者 — 公司最後一次透過 104 站內回覆是幾天前,超出 30 天顯示「無紀錄」
・應徵 — 精確人數(104 頁面上只給 0~5 / 6~10 / 11~30 / 30 人以上的級距)
・刊登 — 原始日期加上換算後的天數,不是 104 顯示的相對時間
・重新刊登 — 本外掛長期追蹤到這個缺被重貼幾次,104 頁面上完全看不到
・公司開缺 — 這家公司同時開幾個缺

點開「說明」只有文字說明與使用注意,沒有額外數據。

▍它不會做的事:評分

這個外掛不評分、不分級,也不推論職缺真假。徽章上只有三種視覺標示:

・綠色 ✓ — 處理履歷或回覆應徵者在 7 天內,是好消息才標;沒有綠色不代表有問題
・紅色 — 這個缺掛了超過 60 天,值得多看一眼,但不是「這是假缺」
・灰底加粗 — 只是提醒刊登日期要換算成天數才有意義

早期版本有一套 0~100 的加權評分與四級分級,後來整套移除,因為實測資料撐不住那些扣分:
抽樣 1,039 個職缺後發現,刊登超過 60 天的缺有 89.7% 的 HR 仍在七天內處理履歷,
超過 180 天的三筆是 100%——掛得久多半是常年開缺(養人才庫、高流動率、條件開得硬),
不是幽靈職缺。而「30 天零動作」的那批,刊登天數中位數只有 1 天,是還沒有人投的新缺。

誤判把真職缺標成假的,對求職者和公司都是傷害。憑感覺訂的門檻做不到這件事,
所以現在只把數據擺出來,判斷交給你。

▍隱藏職缺

同一批公司一直出現?可以自己決定要不要繼續看到:

・在職缺卡片徽章右上角按「隱藏」— 封鎖這家公司。之後它的職缺會摺疊成一行,不會整個消失,可以再展開或解除封鎖
・也可以打開「隱藏我投過的」— 這需要先登入 104,外掛才讀得到你投過哪些職缺;未登入時這條規則不會生效,不會誤判
・封鎖用的是公司代碼,不是名稱:公司改名一樣擋得住,同名的不同公司也分得開

不提供「隱藏置頂職缺」。置頂是 104 的付費商品,做一個開關專門把付費曝光濾掉,性質上接近廣告攔截 —— 這個外掛的定位是補上 104 沒顯示的資訊,不是干預它怎麼賣廣告。

這是這個外掛唯一「替你做決定」的地方,但決定是你自己下的——工具只負責記住並執行。

▍2026-09 的變動

104 在 09-04 調整了資料格式,把幾個數值欄位歸零,互動紀錄改用預先算好的描述字串提供。
本外掛已全數對應:

・精確應徵人數改由 104 的應徵分析端點取得,拿不到時才退回級距。
・HR 活躍度沒有可靠的替代來源,已不再顯示,也不再去取。

拿不到就說拿不到,不會用推估值填補。

  快取與觀察紀錄可從彈出視窗一鍵清除;封鎖清單與偏好設定是你主動的選擇,不會被這顆「清除」鈕一併清掉

▍重要的但書

這些數字有它的邊界,講清楚比講得漂亮重要:

・「無紀錄」不等於「從來沒有」。處理履歷與回覆都是 30 天的滾動紀錄(實測 1,056 筆,兩者「N 天內」的最大值都正好是 30)。超出時間窗就顯示「無紀錄」。

・104 只看得到站內訊息。很多 HR 是直接打電話或寄 email 聯絡應徵者,那些完全不會出現在這個欄位——這也是回覆狀況不列入計分的原因。

・「處理履歷」不一定是真人動作。104 會做系統自動配對推薦,那類動作可能也算在內。實測過所有欄位,沒有任何欄位能分辨真人與系統,所以這個外掛也分不出來。

▍其他限制

・104 沒有公開「首次刊登日期」,appearDate 只是最後更新日,真正的刊登時長要靠外掛長期累積觀察紀錄
・應徵人數只有搜尋 API 有,公司頁與職缺內頁需要用公司名稱回查才能補上;公司名稱夠特殊時能完整對上,名稱通用時只撈得到一部分,對不到的就不顯示,不會亂猜
・依賴 104 未公開文件的 API,對方改版可能失效

```

```
用於在使用者本機存放以下資料:(1) 104 API 回應的快取,依資料類型於 5 分鐘至 6 小時後失效,避免對同一職缺重複發出請求、減少對 104 伺服器的負擔;(2) 職缺的重新刊登觀察紀錄,用來計算某個職缺被重貼過幾次;(3) 使用者自己在徽章或彈出視窗設定的隱藏規則——封鎖的公司清單(以公司代碼儲存,不存公司名稱以外的識別資訊)與「隱藏已投遞」開關,只有使用者主動操作才會寫入;(4) 使用者的啟用/停用偏好設定,以及資料來源健康狀態(連續請求失敗的次數與時間戳記,用來在失敗次數異常時提示使用者「104 可能又改版了」,不含任何個人資料)。以上皆只存在 chrome.storage.local,不會離開使用者的裝置。彈出視窗的「清除」只清掉 (1)(2) 與健康狀態這類可重新取得的快取與紀錄,不會動到使用者自己設定的隱藏規則與啟用/停用開關——那些是使用者主動的選擇,不是快取。
```

## 送審注意事項

- **商標**:名稱與描述都已標註「非官方」並加上與 104 無隸屬關係的聲明。這是降低商標檢舉風險的必要措施,審核或日後有爭議時不要拿掉。
- **單一用途**:manifest 的 `content_scripts.matches` 僅限 104 三種頁面,與 Single purpose 描述一致,不要為了未來功能先放寬。
- **描述必須與實際行為一致**:v1.7.0 移除了整套評分、分級與「機會」徽章,改成中性呈現數據。
  2026-09-10 這次核對發現文案其實**沒有真的同步過**——Summary 與 Single purpose description
  兩處都還留著「標出少人應徵的新缺」這種機會徽章時代的說法,已經修掉;同時補上了 v1.8.0
  才新增的「隱藏職缺」功能說明。日後改動呈現方式或新增功能,送審前務必逐句對照程式碼,
  不要只看上一版文案有沒有變 —— 描述與實際功能不符是常見退件理由。**這一版連截圖一起重拍**,
  舊截圖裡的分數與「機會」徽章在新版不存在了,而且下架後新增的隱藏功能舊圖也拍不到。
- **隱藏功能不要跟廣告攔截混為一談**:v1.8.0 的「隱藏職缺」刻意不做「隱藏置頂職缺」,
  因為置頂是 104 的付費商品,做這個開關性質上接近廣告攔截,會給對方一個站得住腳的法律理由。
  文案與 Single purpose description 裡都只描述「使用者自己封鎖公司/隱藏已投遞」,不要
  加進任何暗示會過濾贊助內容或廣告的說法。
- **不要在外掛裡加 email 或任何蒐集**:Data usage 認證已聲明九項資料類型全不勾。
  訂閱功能刻意做在 GitHub Pages 網站上,兩者互不影響,不要把它挪進外掛。
- **商店評價邀請刻意不加回來**:v1.7.0 移除時把 `util.js` 的使用量統計一併拿掉了。
  重新上架不代表要恢復它 —— 那類本機計數本身就是被刻意移除的,商店上架也不強制要有
  評價邀請。除非之後有新的理由,否則不要為了「以前有過」就加回去。
- **權限最小化**:目前只用 `storage` 與單一 host permission,沒有 `tabs`、`scripting`、`webRequest`,也沒有 background service worker。v1.8.0 的隱藏功能刻意把「這一頁隱藏了幾筆」走 storage 中繼而不是訊息傳遞,就是為了不必加 `tabs` 權限。審核時這是加分項,新增權限前先想清楚理由怎麼寫。
