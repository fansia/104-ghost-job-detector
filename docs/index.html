在 104 人力銀行的職缺上,把 104 手上有、但頁面上不顯示的那半邊數據直接印出來。

第三方獨立開發,非 104 人力銀行官方產品

2026-09 的改版與調整

2026-09-04,104 調整了資料格式,三項資訊同時消失:HR 上次處理履歷的精確時間戳、 應徵人數的精確數字、HR 活躍度百分位。當時一度判斷這個外掛已經沒有存在的必要,並發出了停用公告。

  • 精確應徵人數救回來了。改走 104 的應徵分析端點,拿得到「6 人」而不只是「6~10 人」—— 實測級距 1(0~5 人)佔了全部職缺的 88.9%,級距幾乎沒有分辨力。
  • HR 活躍度不再顯示,也不再去撈。剩下的布林值只有 27% 是 true, 另外七成分不出中段班和墊底;要拿真正的百分位得多打四到六次請求還會靜默失效,不值得。
  • 整套評分與分級移除了。不是因為資料不夠,而是實測資料撐不住那些扣分 —— 理由見下方〈為什麼不評分〉。

謝謝這幾天回報問題的每一位。特別是指出「無紀錄不等於從未回覆」的那位, 以及回報「明明面試過的公司卻被標成無紀錄」的那位 —— 兩次都是在阻止這個工具冤枉真實的公司。 現在的版本不再對任何職缺下判斷,只把數據擺出來。

它解決什麼問題

104 的資料庫其實記錄了每個職缺「上次處理履歷」和「上次回覆應徵者」的時間, 而且 104 網頁自己載入職缺時就會把這些欄位抓回你的瀏覽器。但 104 只會在頁面上顯示正面的那一半 (例如「7 天內處理過履歷」),從不告訴你這家公司近 30 天內一個應徵者都沒回覆過。

這個外掛把另一半補上。每張職缺卡片會多出一列徽章:

方式二:手動安裝(想搶先用最新版)

  1. 到 最新版本頁面 下載 ghost-job-detector-x.y.z.zip,解壓縮到一個你不會刪掉的資料夾。
  2. 打開 Chrome,在網址列輸入 chrome://extensions/ 後按 Enter。
  3. 把右上角的「開發人員模式」打開。 裝好之後也要保持開啟 —— 關掉它,這個外掛就會被 Chrome 一起停用。

  5. 到 104 找工作 搜尋任何職缺, 徽章就會出現在每張卡片上。

手動安裝不會自動更新;有新版時請回到 Releases 重新下載,並在 chrome://extensions/ 點該外掛的「重新載入」。 另外 Chrome 每次啟動可能會提醒你「停用開發人員模式的擴充功能」—— 點「保留」即可。

裝了但沒反應?

依照最常見的順序檢查:

  1. 「開發人員模式」被關掉了。 這是最常見的原因。手動安裝的擴充功能靠它才能執行,安裝完把它關掉,外掛就會一起被停用。 到 chrome://extensions/ 確認右上角的開關是開的。
  2. 安裝後沒有重新整理 104 的頁面。 外掛只會在頁面載入時注入,已經開著的分頁要重新整理一次。
  3. 頁面不在支援範圍內。 目前只在 104 的搜尋結果、AI 推薦、職缺內頁和公司頁運作, 其他頁面(例如首頁、履歷管理)不會有徽章。
  4. 外掛被自己關掉了。 點瀏覽器工具列上的外掛圖示,確認「啟用偵測」是開的。
  5. Chrome 啟動時跳出「停用開發人員模式的擴充功能」。 點「保留」,不要點停用。

如果徽章出現但寫著「無法取得資料」或「資料格式可能已變更」,那多半是 104 改版了。 外掛的彈出視窗會顯示連續失敗的次數,麻煩到 GitHub Issues 回報。

徽章上有什麼

數據在收合狀態就全部呈現,不做摘要;點開「說明」只有文字說明與使用注意,沒有額外數據。

項目104 自己有顯示嗎
處理履歷只顯示有紀錄的情況,無紀錄時整行消失
回覆應徵者同上
應徵人數(精確)只給級距(0~5 / 6~10 / 11~30 / 30 人以上)
刊登日期 + 距今天數只給日期,不換算
重新刊登次數完全看不到,由本外掛長期觀察累積
公司同時開缺數公司頁有,職缺頁沒有

只有三種視覺標示,都不是分級:綠色 ✓ 是處理履歷或回覆 ≤ 7 天(好消息); 紅色 是刊登超過 60 天(值得多看一眼,不是「這是假缺」); 灰底加粗只是提醒刊登日期要換算成天數才有意義。

為什麼不評分

早期版本有一套 0–100 的加權評分與四級分級(正常 / 留意 / 可疑 / 高風險),後來整套移除。 原因是 2026-09-05 做的一次抽樣(10 個關鍵字 × 第 1/3/6/10/15 頁,1,039 個不重複職缺) 顯示那些扣分規則的前提站不住。

「掛越久越沒人管」不成立 —— 掛越久的缺,HR 反而越沒問題:

刊登筆數HR 七天內仍在處理履歷30 天零動作
> 30 天89 (8.6%)93.3%0
> 60 天39 (3.8%)89.7%0
> 90 天15 (1.4%)86.7%0
> 180 天3 (0.3%)100%0

掛超過半年的三筆,HR 全部七天內還在處理履歷。那是常年開缺 (養人才庫、高流動率、條件開太硬),不是幽靈職缺。

「30 天零動作」的那批也不是幽靈,是新缺:n = 34,刊登天數中位數 1 天、 應徵人數全部落在 0~5 人那一檔,104 自己還給其中 41% 掛了「積極徵才中」。 而「零動作且6 人以上應徵過」這種真正說得過去的組合,樣本裡一筆都沒有。 兩個訊號也幾乎不重疊(刊登 > 30 天且零動作:0 筆)—— 它們是兩種不同的病, 加總成一個分數只會讓兩種問題長成同一個數字。

一併移除的還有綠色的「機會」徽章:它實測掛在 33.3% 的職缺上, 三個缺就有一個是「機會」,等於沒說話。

誤判把真職缺標成假的,對求職者和公司都是傷害。 憑感覺訂的門檻做不到這件事,所以現在只呈現數據,判斷交給你。程式碼在 src/score.js。

  • 104 沒有公開「首次刊登日期」,appearDate 只是最後更新日。真正的刊登時長要靠外掛長期累積觀察紀錄。
  • 精確應徵人數來自 104 的應徵分析端點。該端點對不存在的職缺編號一律回 200 + total: 0,跟真的 0 人應徵長得一模一樣,所以要拿級距交叉驗證; 端點失敗時只顯示級距。
  • HR 的「處理履歷」不一定是真人動作。104 會做系統自動配對推薦,那類動作可能也算進 處理紀錄。實測過所有欄位,沒有任何欄位能分辨真人與系統動作 —— 看到「HR 昨天處理過履歷」時請保留一點餘地。
  • 依賴 104 未公開文件的 API,對方改版可能失效。
  • 抽樣是從搜尋結果來的,而搜尋結果本身就是照符合度排序、篩過的 —— 刻意翻到第 15 頁, 看到的仍然只是那個關鍵字的 0.24%。正確的結論是「在你實際會看到的職缺裡 沒有值得標的極端案例」,不是「這種缺不存在」。
