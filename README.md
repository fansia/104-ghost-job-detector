# 幽靈職缺偵測器(104 非官方)

在 104 人力銀行的職缺上,把 **104 手上有、但頁面上不顯示的那半邊數據** 直接印出來。

> 本專案由第三方獨立開發,**與 104 資訊科技股份有限公司無任何隸屬或合作關係**。
> 「104」為其權利人之商標,此處僅用於說明本外掛的適用範圍。

📖 [安裝說明頁面](https://fansia.github.io/104-ghost-job-detector/)

> [!NOTE]
> ## 2026-09 的改版與調整
>
> **2026-09-04,104 調整了資料格式**,三項資訊同時消失:HR 上次處理履歷的精確時間戳、
> 應徵人數的精確數字、HR 活躍度百分位(`hrBehaviorPR`)。當時一度判斷這個外掛
> 已經沒有存在的必要,並發出了停用公告。
>
> **2026-09-05 之後的現況:**
>
> - **精確應徵人數救回來了。** 改走 104 的應徵分析端點,拿得到「6 人」而不只是「6~10 人」。
>   實測級距 1(0~5 人)佔了全部職缺的 88.9%,其中真的 0 人的只有 7.5% ——
>   級距幾乎沒有分辨力,精確數字才有。
> - **HR 活躍度不再顯示,也不再去撈。** 剩下的 `hasHrBehavior` 布林值只有 27% 是 true,
>   false 涵蓋剩下的七成、分不出中段班和墊底;要拿到真正的百分位得靠相似職缺清單反查,
>   單一職缺多打四到六次請求還會靜默失效,不值得。
> - **整套評分與分級移除了。** 理由不是資料不夠,而是實測資料撐不住那些扣分 ——
>   見下面〈為什麼不評分〉。徽章改成中性呈現數據,不下判斷。
>
> 所以這個外掛還在做的事,是 104 頁面上看不到的那幾項:精確應徵人數、
> 「近 30 天內無處理/無回覆紀錄」(104 只在有紀錄時顯示那一行)、以及重新刊登次數。

104 的資料庫其實記錄了每個職缺「上次處理履歷」和「上次回覆應徵者」的時間,而且 104 網頁自己載入職缺時就會把這些欄位抓回瀏覽器——但 104 只會在頁面上顯示正面的那一半(例如「7 天內處理過履歷」),從不告訴你這家公司**近 30 天內一個應徵者都沒回覆過**。這個外掛把另一半補上。

## 安裝

**Chrome 線上應用程式商店(建議):**[前往安裝](https://chromewebstore.google.com/detail/ollabfbopbnckocijfnahjeaoalbnbej) —— 一鍵安裝,自動更新。

> 商店版本可能落後 [Releases](https://github.com/fansia/104-ghost-job-detector/releases/latest) 一段時間:
> 每次改版都要重新送審,審查通常要數週。想搶先用最新版就用下面的手動安裝。

**手動安裝(想搶先用最新版):**

1. 到 [Releases](https://github.com/fansia/104-ghost-job-detector/releases/latest) 下載 zip 並解壓縮
   (或直接 clone 本專案)
2. 打開 Chrome,進入 `chrome://extensions/`
3. 開啟右上角的「開發人員模式」(**裝好後也要保持開啟**,關掉外掛就會被停用)
4. 點「載入未封裝項目」,選擇解壓縮後的資料夾
5. 到 [104 找工作](https://www.104.com.tw/jobs/search/) 搜尋任何職缺

> 手動安裝不會自動更新。有新版時回到 Releases 重新下載,
> 並在 `chrome://extensions/` 點該外掛的「重新載入」。

### 裝了但沒反應?

依照最常見的順序檢查:

1. **「開發人員模式」被關掉了** —— 最常見的原因。手動安裝的擴充功能靠它才能執行。
2. **安裝後沒有重新整理 104 的頁面** —— 外掛只在頁面載入時注入。
3. **頁面不在支援範圍** —— 只在搜尋結果、AI 推薦、職缺內頁、公司頁運作。
4. **外掛被自己關掉了** —— 點工具列圖示確認「啟用偵測」是開的。
5. **Chrome 啟動時跳出「停用開發人員模式的擴充功能」** —— 點「保留」。

如果徽章出現但寫著「無法取得資料」,多半是 104 改版了。彈出視窗會顯示連續失敗次數,
麻煩到 [Issues](https://github.com/fansia/104-ghost-job-detector/issues) 回報。

## 它會顯示什麼

每個職缺卡片和職缺內頁會多出一列數據,收合狀態就全部呈現,不做摘要:

```
處理履歷 ✓ 3 天前   回覆應徵者 近 30 天內無紀錄   應徵 6 人                  說明 ▾
刊登 2026/07/02(65 天前)   重新刊登 2 次   公司開缺 885 個
```

| 項目 | 說明 | 104 自己有顯示嗎 |
|---|---|---|
| 處理履歷 | HR 最後一次點開履歷是幾天前 | 只顯示有紀錄的情況,無紀錄時整行消失 |
| 回覆應徵者 | 公司最後一次透過 104 站內回覆是幾天前 | 同上 |
| 應徵 | **精確人數**,取不到時退回級距 | 只給級距(0~5 / 6~10 / 11~30 / 30 人以上) |
| 刊登 | 原始日期 + 換算成幾天前 | 只給日期,不換算 |
| 重新刊登 | 本外掛長期追蹤到這個缺被重貼幾次 | ❌ 完全看不到 |
| 公司開缺 | 這家公司同時開幾個缺 | 公司頁有,職缺頁沒有 |

只有三種視覺標示,都不是分級:

| 標示 | 條件 | 意思 |
|---|---|---|
| ✓ 綠色 | 處理履歷或回覆應徵者 ≤ 7 天 | 好消息 —— HR 這幾天真的在動 |
| 紅色 | 刊登超過 60 天 | 值得多看一眼,**不是**「這是假缺」 |
| 灰底加粗 | 刊登 60 天以內 | 這個欄位要換算成天數才有意義 |

點開「說明」只有文字說明與使用注意,沒有額外數據。

## 為什麼不評分

早期版本有一套 0~100 的加權評分與四級分級(正常 / 留意 / 可疑 / 高風險),
後來整套移除。原因是 2026-09-05 做的一次抽樣(10 個關鍵字 × 第 1/3/6/10/15 頁,
1,039 個不重複職缺)顯示,那些扣分規則的前提站不住:

**「掛越久越沒人管」不成立 —— 掛越久的缺,HR 反而越沒問題:**

| 刊登 | 筆數 | HR 七天內仍在處理履歷 | 30 天零動作 |
|---|---|---|---|
| > 30 天 | 89 (8.6%) | 93.3% | 0 |
| > 60 天 | 39 (3.8%) | 89.7% | 0 |
| > 90 天 | 15 (1.4%) | 86.7% | 0 |
| > 180 天 | 3 (0.3%) | **100%** | 0 |

掛超過半年的三筆,HR 全部七天內還在處理履歷。那是**常年開缺**
(養人才庫、高流動率、條件開太硬),不是幽靈職缺。

**「30 天零動作」的那批也不是幽靈,是新缺:** n = 34,刊登天數中位數 **1 天**、
應徵人數全部落在 0~5 人那一檔,104 自己還給其中 41% 掛了「積極徵才中」。
而「零動作 **且** 6 人以上應徵過」這種真正說得過去的組合,樣本裡 **一筆都沒有**。

**兩個訊號幾乎不重疊**(刊登 > 30 天且零動作:0 筆),證明它們是兩種不同的病,
加總成一個分數只會讓兩種問題長成同一個數字。

再加上 `hrBehaviorPR` 被 104 移除後,每個壞缺整整少 30 分,而分級線沒動 ——
實測 150 筆的最高分是 30 分,而「可疑」的門檻是 40,後兩格根本是死的。
一併移除的還有綠色的「機會」徽章:它實測掛在 **33.3%** 的職缺上,
三個缺就有一個是「機會」,等於沒說話。

**誤判把真職缺標成假的,對求職者和公司都是傷害。** 憑感覺訂的門檻做不到這件事,
所以現在只呈現數據,判斷交給使用者。

## 資料來源

全部來自 **104 網頁前端自己使用的內部 JSON API**,以同源請求在使用者自己的瀏覽器中發出,
不經過任何第三方伺服器:

| 用途 | 端點 |
|---|---|
| 搜尋結果 | `GET /jobs/search/api/jobs` |
| 職缺內頁 | `GET /job/ajax/content/{jobCode}` |
| 公司職缺(含 `interactionRecord`) | `GET /api/companies/{custCode}/jobs` |
| 精確應徵人數 | `GET /jb/104i/applyAnalysisToJob/all?job_no={jobNo}` |

> **這不是 104 官方開放的 API。** 104 官方對外開放的是給企業串接的職缺刊登/管理 API,
> 以及給求職端的職缺搜尋 Open API,兩者都要申請金鑰,欄位也沒有細到 HR 的回覆紀錄。
> 本外掛用的是 104 網頁載入職缺卡片時自己會去打的內部端點,未公開文件,
> 也因此隨時可能改版失效。

`interactionRecord` 是關鍵欄位。2026-09 改版後三個時間戳全部歸零,
真正的資料改放進兩個中文字串:

```json
{
  "lastProcessedResumeDesc": "3天內處理過履歷",
  "lastCustReplyDesc": "",
  "lastProcessedResumeAtTime": 0,
  "lastCustReplyTimestamp": 0,
  "nowTimestamp": 1788228579
}
```

空字串代表這個職缺**近 30 天內沒有**該項紀錄。程式用「有沒有 `...Desc` 這個 key」
判斷格式,而不是看值是不是 0 —— 真的沒有互動紀錄的職缺也會是 0,兩者必須分得開;
104 若改回舊格式也會自動走回時間戳那條路。

> ### 這兩個欄位是滾動時間窗,不是全部歷史
>
> 改版後兩者都是 **30 天**(實測 1,056 筆,「N 天內」的最大值都正好是 30;
> 改版前處理履歷是 30 天、回覆是 90 天)。
>
> 所以「無紀錄」的意思是「**這段期間內沒有**」,不是「從來沒有」。
>
> 另外,104 只記錄得到**站內訊息**的往來。HR 若直接打電話或寄 email 聯絡應徵者,
> 這裡不會有紀錄 —— 「無回覆紀錄」不等於「這家公司不理人」。

- 不蒐集、不上傳任何資料

### 幾個實作上的坑

- **搜尋結果用 `vue-recycle-scroller`**,卡片 DOM 會被回收重用。每次注入前都要比對 `data-job-no`,並在 await 前後確認卡片還是同一個職缺,否則徽章會貼到別的職缺上。
- **搜尋 API 一頁不一定回 20 筆**(有置頂職缺時會更多),所以不能用卡片索引推算頁碼,要從第一頁循序往後找。
- **同一頁會被多張卡片同時請求**,必須共用同一個 Promise 並等它完成;先標記「已取得」再去 fetch 會讓後到的呼叫拿到空資料。
- **content script 跑在 isolated world**,不受 104 頁面 CSP 的 `connect-src` 限制。

## 已知限制

- 104 沒有公開「首次刊登日期」,`appearDate` 只是最後更新日。真正的刊登時長要靠外掛長期累積觀察紀錄。
- 精確應徵人數來自應徵分析端點。該端點對「不存在的 job_no」「參數是 0 或非數字」
  全都回 `200` + `total: 0`,跟真的 0 人應徵長得一模一樣,所以要拿級距交叉驗證:
  級距說有 6 人以上、精確值卻是 0,就退回級距。端點失敗時只顯示級距。
- HR 的「處理履歷」不一定是真人動作。有讀者指出 104 會做系統自動配對推薦,
  那類動作可能也算進處理紀錄。實測過職缺頁與各支 API 的所有欄位,
  **沒有任何欄位能分辨真人與系統動作**,所以這個外掛也分不出來 ——
  看到「HR 昨天處理過履歷」時請保留一點餘地。
- 依賴 104 未公開文件的 API,對方改版可能失效。
- 抽樣是從搜尋結果來的,而搜尋結果本身就是照符合度排序、篩過的。刻意翻到第 15 頁
  仍然只看到那個關鍵字的 0.24%。所以正確的結論是「**在使用者實際會看到的職缺裡**
  沒有值得標的極端案例」,不是「這種缺不存在」。
